# Brim x402 integration

Brim pays x402 APIs through your agent's on-chain spending policy. The agent holds a scoped key; the vault keeps the treasury funds.

## Agent quickstart

Your operator supplies a public vault config (Brim card) and authorizes your scoped agent key on-chain. Application setup needs two values:

```ts
import { createBrimFetch } from '@brim/sdk';

const brimFetch = createBrimFetch({
  card: process.env.BRIM_CARD!,
  agentKey: process.env.BRIM_AGENT_KEY!,
});

const response = await brimFetch('https://merchant.example/v1/data');
```

`BRIM_CARD` contains public routing metadata: the vault, program, network, and trusted facilitator fee payers. It creates no policy and grants no authority. `BRIM_AGENT_KEY` is private: a JSON array of the scoped agent's 64 Ed25519 keypair bytes. Never use the treasury owner's key.

This is a private workspace package, not an npm publication. The URL above is illustrative; follow the [repository quickstart](../README.md#start-everything-locally) for a runnable payment with fake funds, or the [SDK README](../packages/sdk/README.md) for the standalone example.

## Optional RPC connection

Brim selects Solana's public RPC from the trusted network in your config:

| Network | Default                               |
| ------- | ------------------------------------- |
| Mainnet | `https://api.mainnet-beta.solana.com` |
| Devnet  | `https://api.devnet.solana.com`       |

For a dedicated provider or local Surfpool, add `rpcUrl: process.env.SOLANA_RPC_URL`. Explicit URLs are validated, and the RPC's genesis must still match the configured network. No RPC work occurs during setup or for a free response. Provider credentials never belong in the public card.

The SDK adds a $1 USDC safety cap per payment. Add `maxPaymentAmount: 5_000_000n` for a $5 local cap; the on-chain policy remains authoritative.

## Operator handoff

Create the public config after preparing the vault, registering the agent policy, and confirming facilitator compatibility:

```ts
import { createBrimCard } from '@brim/sdk';

const card = createBrimCard({
  vaultAddress: process.env.BRIM_VAULT_ADDRESS!,
  programAddress: process.env.BRIM_PROGRAM_ADDRESS!,
  network: 'solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1', // devnet
  facilitatorFeePayers: [process.env.BRIM_FACILITATOR_FEE_PAYER!],
});
```

Hand `card` to the application as `BRIM_CARD`, separately from its private agent key. `createBrimCard` only serializes validated metadata; it does not deploy a program, register a policy, or move funds. Advanced integrations may still pass `BrimConfig` directly; its `rpcUrl` is optional too.

## Runtime and errors

`createBrimFetch` is a normal Promise-based fetch function. Effect applications can use the lazy `createBrimFetchEffect` with the same two inputs. Errors use the tagged `BrimPolicyViolationError` and its stable `code`.

A frozen agent, exhausted budget, or unapproved recipient fails before signing when detected locally. The program enforces the same rules at execution. `PAYMENT_OUTCOME_UNKNOWN` means settlement is uncertain: reconcile the original payment before creating another authorization. The SDK does not promise invoice idempotency.

## Facilitator operator configuration

**Facilitator support is explicit.** In `@x402/svm` 2.32.0, default `exact` validation accepts a top-level token transfer. A Brim payment transfers through CPI and therefore requires the new smart-wallet verification path, enabled by the facilitator operator with the deployed Brim program on its allowlist. A merchant advertising ordinary `exact` payments is not evidence that its facilitator supports Brim. Confirm support with its operator and pin the facilitator's fee payer addresses in your client config. The SDK refuses configuration without that affirmation.

This is the actual current SDK API; it configures an instance for an existing facilitator HTTP service, rather than creating hosted `/verify` and `/settle` endpoints by itself:

```ts
import { x402Facilitator } from '@x402/core/facilitator';
import { ExactSvmScheme } from '@x402/svm/exact/facilitator';
import { toFacilitatorSvmSigner } from '@x402/svm';
import type { MessagePartialSigner, TransactionSigner } from '@solana/kit';

function makeBrimFacilitator(
  feePayerSigner: TransactionSigner & MessagePartialSigner,
  programAddress: string,
  rpcUrl: string,
) {
  const signer = toFacilitatorSvmSigner(feePayerSigner, {
    defaultRpcUrl: rpcUrl,
  });
  const scheme = new ExactSvmScheme(signer, undefined, {
    enableSmartWalletVerification: true,
    smartWalletAllowedPrograms: [programAddress],
    smartWalletMaxComputeUnits: 200_000,
    smartWalletMaxPriorityFeeMicroLamports: 1,
    maxRequiredSignatures: 2,
    transactionVersions: [0],
    // For multiple replicas, inject a shared PendingSettlementStore here.
  });
  return new x402Facilitator().register('solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1', scheme);
}
```

The built-in signer supplies simulation inner instructions, fee payer isolation, signature verification, and confirmed-transfer verification used by the current exact verifier. The operator owns the fee payer's SOL expense, RPC configuration, durable cross-replica settlement reconciliation, and endpoint authentication/rate limiting. No facilitator private key belongs in the agent or web dashboard. Production facilitator deployment remains an integration task. The local stack includes an in-process facilitator using fake Surfpool keys and binds it only to loopback.

## Payment behavior

- Accepts one compatible x402 v2 `exact` offer, on the configured Solana network, for the official USDC mint.
- Reads fresh vault and policy state before signing. Budgets use fixed windows, rate limits enforce minimum payment spacing, and allowlists contain recipient pubkeys rather than domains.
- Builds a v0 `execute_payment` transaction with a strict `transfer_checked` CPI. It never creates token approvals. The agent signs; the isolated facilitator fee payer co-signs and broadcasts.
- Retries the original HTTP request once with its payment authorization. Redirects and pre-existing payment headers are refused. HTTPS is required, with localhost HTTP allowed for development.
- Optional `onEvent` callbacks are client observations, not proof of settlement. The indexer independently verifies finalized runtime events.

The recipient's USDC associated token account must already exist. The checked-in program identity is for development; a live deployment requires its own verified setup.

## Verification and remaining work

`packages/sdk/tests/` covers integer precision, overflow, fixed-window boundaries, freeze/pause/allowlist checks, untrusted sponsor rejection, unsupported/malformed/ambiguous offers, HTTP authorization rejection, POST body preservation, bounded paid retries, and actual Kit v0 signing. It also passes the generated payment to the **real current exact facilitator verifier**, demonstrating that default verification rejects it, opt-in verification accepts a matching simulated USDC CPI transfer, and a recipient mismatch is rejected.

Those unit tests use RPC and CPI fixtures. The separate offline integration flow executes the compiled Brim program on Surfpool and uses the real x402 verifier and settler. It verifies a $0.04 vault debit, the matching merchant credit, the settlement signature, a finalized `PaymentExecuted` event, and one idempotent Postgres ledger row.

With the local stack running, exercise it from another terminal:

```sh
npm run demo:payment
```

`npm run test:local` owns the full local test lifecycle. Local credentials are generated in the ignored `.brim/local.json`; the scripts do not print them. Surfpool runs offline, and every SOL/USDC balance is fake. This verifies the repository's local integration; public devnet settlement, a production facilitator's support, and independent contract audit remain release prerequisites.
