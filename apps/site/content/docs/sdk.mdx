Brim needs two values: the public vault config (`BRIM_VAULT_CONFIG`) and your agent's scoped keypair (`BRIM_AGENT_KEY`). The config tells Brim where to connect. The key selects the on-chain spending policy that your operator registered for this agent.

## Use two inputs

```ts title="agent.ts"
import { createBrimFetch } from '@brim/sdk';

const brimFetch = createBrimFetch({
  vaultConfig: process.env.BRIM_VAULT_CONFIG!,
  agentKey: process.env.BRIM_AGENT_KEY!,
});

const response = await brimFetch('https://merchant.example/paid-resource');
```

The URL is illustrative. The [quickstart](/docs/quickstart/) makes a real local payment with fake funds. `@brim/sdk` is a private workspace package, not a published npm package.

## Get your local config

Start the [local stack](/docs/quickstart/) with `npm run dev`. It creates a funded test vault and a starter policy. Open a registered policy's **Code setup** and choose **Copy setup**. Every agent on this local vault can reuse its public vault config; each agent supplies its own private key.

The private test values stay in ignored `.brim/` files. The built-in payment runner loads its starter key automatically. To attach your own agent, register its public key below and keep its private key in that agent's runtime.

## Register your agent locally

1. **Prepare a scoped key.** Reuse your agent's existing Ed25519 keypair, or generate one from the repository root:

```bash
npm run agent:key -- --out .brim/research-agent.json
```

The helper creates a new mode-`0600` keypair file and prints only `publicKey` and `keyFile`. It refuses to overwrite an existing file. Copy the public key; do not paste the private JSON into the dashboard.

2. **Attach a policy.** Open **Local workspace → Add policy**, paste that public key, and set a **$1 per-payment cap** and **$50 24-hour budget**. Advanced settings hold payment spacing and recipient restrictions. Choose **Add policy** and wait for on-chain confirmation.

3. **Inspect the registration.** Your agent appears in the list. Its detail sheet shows a copyable registered public key. Open **Code setup** to **Copy setup** or **Check connection**. Editing limits preserves consumed budget, frozen state, window timing, and any spacing you leave unchanged.

4. **Run the agent.** With `jq` installed, run this in another terminal at the repository root:

```bash
export BRIM_VAULT_CONFIG="$(jq -r '.vaultConfig' .brim/local.json)"
export BRIM_AGENT_KEY="$(jq -c . .brim/research-agent.json)"
export SOLANA_RPC_URL="$(jq -r '.rpcUrl' .brim/local.json)"

node packages/sdk/examples/agent.ts http://127.0.0.1:4020/report
```

These assignments load values without displaying the keypair. The report costs **$0.04 fake USDC**; a successful example prints `HTTP 200`. Use your existing private key file instead if you skipped key generation. Do not enable shell tracing or print the environment.

The local RPC override is necessary: the public default devnet RPC cannot see your Surfpool vault. If you enable a recipient allowlist, include the report merchant's public key, available with `jq -r '.merchantAddress' .brim/local.json`.

Every successful local `/report` settlement is queued for independent finalized verification and indexing, including your SDK and MCP calls. Activity may appear after `HTTP 200`; that response alone is not proof of finality. The [built-in payment test](/docs/quickstart/#pay-for-the-report) also checks both token balances and the ledger.

For the same agent in a tool-based client, use [MCP with your local key file](/docs/mcp/#connect-your-own-local-agent). Local funding, withdrawals, and freezes remain read-only; use the [configured owner-wallet flow](/docs/production/#follow-the-owner-wallet-flow) for those live actions.

## What the values look like

- **`BRIM_VAULT_CONFIG` is one string beginning with `brim:v1:`**, such as `brim:v1:eyJ2ZXJzaW9uIjoxLC...`. It contains the vault address, program address, network, and trusted facilitator fee payers. Your operator supplies the complete string.
- **`BRIM_AGENT_KEY` is a JSON array of exactly 64 numbers**, each from 0 to 255, such as `[12,34,56,...]`. Use the full standard Solana Ed25519 keypair export as a string in your private runtime configuration; the SDK decodes it.

The examples are abbreviated; copy the complete values into your runtime. The private keypair stays in the integrator's runtime or secret store. The operator needs only its corresponding **public key** to authorize spending. Use a separate scoped keypair for the agent.

## Who hands over what

1. **The agent integrator generates a scoped keypair.** Keep its private 64-byte keypair export with the application and send its public key to the treasury operator.
2. **The operator registers that public key and its limits on the vault.** Use Local workspace for test funds, or the [configured owner-wallet path](/docs/production/#follow-the-owner-wallet-flow) for an existing deployed vault. The operator also prepares funding and a compatible facilitator.
3. **The operator creates and shares the public vault config.** The returned `brim:v1:...` string becomes `BRIM_VAULT_CONFIG`.
4. **The integrator supplies both values to the application.** Load the public config as `BRIM_VAULT_CONFIG` and the matching private keypair as `BRIM_AGENT_KEY` through the runtime's configuration.

Agents using the same vault, program, network, and trusted fee-payer list can reuse the same vault config string. Each agent keeps its own keypair and has its own policy. Sharing the public config grants no spending authority.

## Create and share the public config

Operators can also build the public string after preparing the [vault and policy](/docs/vaults-and-policies/). For local Surfpool, replace these placeholders with the vault address and trusted facilitator fee payer address from your local setup:

```ts title="local-operator.ts"
import { createBrimVaultConfig, BRIM_DEVELOPMENT_PROGRAM_ADDRESS } from '@brim/sdk';

const vaultConfig = createBrimVaultConfig({
  vaultAddress: 'YOUR_LOCAL_VAULT_ADDRESS',
  programAddress: BRIM_DEVELOPMENT_PROGRAM_ADDRESS,
  network: 'devnet',
  facilitatorFeePayers: ['YOUR_LOCAL_FEE_PAYER'],
});
```

The development program address is for local Surfpool only. For a public deployment, set `programAddress` to its actual deployed address and choose `'devnet'` or `'mainnet'`. Confirm the trusted fee payers with the [facilitator operator](/docs/x402/). The SDK translates the network name to its x402 identifier.

Share the returned `vaultConfig` string with the integrator. Use `readBrimVaultConfig(vaultConfig)` to inspect its public settings.

The policy's **Code setup → Copy setup** copies public connection settings and a runtime template. It does not copy or generate an agent private key. **Check connection** checks policy and setup without sending payment. You may supply an optional merchant URL to inspect its public quote; browser CORS restrictions can prevent that lookup. A matching quote cannot establish that the facilitator will accept the program or that funds will settle.

## Check a connection without paying

The dashboard's **Check connection** uses a public-key-only check. Application code can use the same check:

```ts
import { checkBrimConnection } from '@brim/sdk';

const report = await checkBrimConnection({
  vaultConfig: process.env.BRIM_VAULT_CONFIG!,
  agentPublicKey: 'YOUR_REGISTERED_AGENT_PUBLIC_KEY',
  // Optional: use your provider, or the local Surfpool URL for local tests.
  rpcUrl: 'http://127.0.0.1:8899',
  // Optional public quote. Omit to check only the chain setup.
  resourceUrl: 'http://127.0.0.1:4020/report',
});

console.log(report.ready, report.blockers);
```

This local example loads **no private signing key**, sends no payment authorization, and does not broadcast a transaction. Replace the local URLs with your configured connection and HTTPS merchant for a public environment. `checkBrimConnectionEffect(input)` is the lazy Effect alternative; the Promise API also accepts `{ signal }` as its second argument.

`ready` means the requested checks passed at the current chain snapshot. Missing policy, freeze/pause, empty vault, consumed budget, and payment spacing appear in `blockers`; invalid account/RPC/quote data fails with a typed `BrimPolicyViolationError`. The JSON-safe report uses integer-string base units and includes the policy's remaining window budget. It is not a reservation or a promise that the agent holds the matching private key.

An optional merchant check makes a GET for its public response/quote, refuses redirects, and does not read the resource body or attach authorization. Browser CORS can block it. `merchant.facilitatorAcceptance` remains **`"unverified"`**, even for a matching quote: facilitator acceptance and actual settlement require a real payment path.

The bundled CLI checks the starter local agent without loading its signing key. With the local stack running and `jq` installed:

```bash
export BRIM_VAULT_CONFIG="$(jq -r '.vaultConfig' .brim/local.json)"
export SOLANA_RPC_URL="$(jq -r '.rpcUrl' .brim/local.json)"

npm run agent:check -- \
  --agent-public-key "$(jq -r '.agentAddress' .brim/local.json)" \
  --resource-url http://127.0.0.1:4020/report
```

For your own agent, replace the public-key argument with its registered public key. Omit `--resource-url` for chain checks only. The CLI prints a public JSON report: exit `0` means the requested checks passed, `2` means policy/setup blockers, and `1` means failure or cancellation. This read-only check never authorizes a payment.

## Optional connection and cap

Brim normally uses Solana's public RPC for the network in your config: `https://api.devnet.solana.com` or `https://api.mainnet-beta.solana.com`.

Add `rpcUrl: process.env.SOLANA_RPC_URL` for a dedicated provider or local Surfpool. Keep provider credentials outside the public vault config. An explicit invalid URL fails rather than silently falling back.

The default SDK safety cap is **$1 USDC per payment**. Add `maxPaymentAmount: 5_000_000n` for a $5 local cap. The on-chain policy still applies.

## API reference

| API                                                 | Input                                                                                       | Return and purpose                                                                                                             |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `createBrimFetch`                                   | `BrimVaultConfig`                                                                           | A standard fetch function: `(input, init?) => Promise<Response>`. Use it in ordinary application code.                         |
| `createBrimFetchEffect`                             | `BrimVaultConfig`                                                                           | `BrimEffectFetch`: the same request inputs produce `Effect<Response, BrimPolicyViolationError>`. Use it in an Effect workflow. |
| `createBrimVaultConfig`                             | Public vault settings, including `network: 'devnet'`, `'mainnet'`, or a supported CAIP-2 ID | A `brim:v1:...` string. Operator setup only; it does not attach a policy.                                                      |
| `readBrimVaultConfig`                               | An encoded config string                                                                    | `BrimVaultConfigDetails`: public settings with a canonical CAIP-2 `network`. No network request or signing occurs.             |
| `checkBrimConnection` / `checkBrimConnectionEffect` | Public vault config, agent public key, optional RPC and resource URL                        | Advisory setup report without private keys, signing, or settlement.                                                            |

Both fetch variants accept standard `RequestInfo | URL` and optional `RequestInit`, preserve the request body, and reject redirects and existing payment authorization headers. A non-402 resource response is returned using normal fetch semantics; inspect `response.ok` or `response.status` separately. A paid error response, including HTTP `503`, does not establish that funds stayed in the vault.

## Typed errors and outcome checks

Failures use `BrimPolicyViolationError`, whose `_tag` is `"BrimPolicyViolationError"` and whose `code` is a `BrimErrorCode`. Promise callers can use `instanceof`; Effect callers can handle the tag. The code is the stable field to branch on. Common codes:

| Code                                                                             | Agent action                                                                                                                           |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `INVALID_CARD`, `UNSUPPORTED_CARD_VERSION`, `INVALID_CONFIG`, `INVALID_ACCOUNT`  | Check the vault config, scoped key, and registered policy with the operator. These existing code names are retained for compatibility. |
| `AGENT_FROZEN`, `VAULT_PAUSED`, `RECIPIENT_NOT_ALLOWED`                          | Stop the paid task and ask the operator to review permission.                                                                          |
| `PER_TRANSACTION_LIMIT_EXCEEDED`, `WINDOW_LIMIT_EXCEEDED`, `RATE_LIMIT_EXCEEDED` | Respect the configured cap, budget, or spacing. Do not raise limits automatically.                                                     |
| `UNSUPPORTED_PAYMENT`, `UNTRUSTED_FEE_PAYER`, `INVALID_PAYMENT_REQUIREMENTS`     | Ask the merchant or facilitator operator for a compatible payment offer.                                                               |
| `RPC_UNAVAILABLE`, `REQUEST_FAILED`, `SIGNING_FAILED`                            | Check the connection or scoped key configuration. These failures occur before payment handoff.                                         |
| `PAYMENT_OUTCOME_UNKNOWN`, `PAYMENT_REJECTED`                                    | Reconcile the original payment before another paid request. A rejected paid HTTP retry does not prove that funds stayed in the vault.  |

Effect cancellation remains an interruption, not a promise of a typed payment result. A canceled paid request may have settled even if no receipt or diagnostic reaches the caller. Reconcile before authorizing another.

A successful HTTP response, receipt, or `onEvent` callback is not independent proof of settlement. Verify the finalized transaction and expected `PaymentExecuted` program event before marking a payment settled. The [quickstart](/docs/quickstart/) demonstrates that verification and a deduplicated ledger record.

Calling fetch again may authorize another payment. Follow the [bounded retry behavior](/docs/x402/#keep-retries-bounded), and confirm [facilitator compatibility](/docs/x402/#configure-a-compatible-facilitator) before using an external paid API.

For a [pay.sh catalog endpoint](/docs/x402/#use-paysh-endpoints), pass the provider's URL to the same `brimFetch` function.
