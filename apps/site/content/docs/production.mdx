Brim has a working offline payment path and wallet-signed dashboard controls. The hosted test deployment serves the site, docs, and a browser demo dashboard. **It does not deploy a public-chain program or enable real payments.** Public devnet settlement, independent security review, and operational release checks remain required before real funds.

## Configure a deployed program

Use an already deployed Brim program whose USDC mint matches the selected network. For local dashboard development, set public values in `apps/web/.env.local` before starting it:

```dotenv
NEXT_PUBLIC_BRIM_LIVE_PROGRAM_ADDRESS=YOUR_DEPLOYED_PROGRAM_ADDRESS
NEXT_PUBLIC_BRIM_LIVE_NETWORK=devnet
NEXT_PUBLIC_BRIM_LIVE_FEE_PAYERS=YOUR_TRUSTED_FACILITATOR_FEE_PAYER
# Optional browser-public HTTPS RPC; omit to use the network default.
NEXT_PUBLIC_BRIM_LIVE_RPC_URL=https://YOUR_PUBLIC_RPC_ENDPOINT
```

`NEXT_PUBLIC_BRIM_LIVE_NETWORK` accepts `devnet` or `mainnet`. Separate multiple trusted fee payer public keys with commas. Confirm that the facilitator [supports Brim](/docs/x402/#configure-a-compatible-facilitator); listing an address does not enable that support.

To pin an existing vault instead, use the supported `NEXT_PUBLIC_BRIM_LIVE_VAULT_CONFIG=brim:v1:...` setup, with the same optional RPC override. Choose one setup style.

All `NEXT_PUBLIC_*` values are shipped to the browser. They must contain only public routing information, never RPC secrets or keypairs. Set them before building; a deployed Next.js bundle needs rebuilding when public configuration changes. `BRIM_DEVELOPMENT_PROGRAM_ADDRESS` is a Surfpool fixture, not a deployed public program.

## Follow the owner-wallet flow

1. Choose **Live workspace** and **Connect owner wallet**. Use an ordinary Solana Wallet Standard signer; Squads-owned vault execution is not integrated.
2. Choose **Create vault** if the connected owner has no vault for this program and mint. Confirm the transaction in the wallet. The owner needs SOL for fees and account rent.
3. Choose **Deposit**, enter a USDC amount, and confirm in the wallet. Funds move from the owner's token account into the vault. **Withdraw** returns funds to the owner through a separate reviewed transaction.
4. Choose **Add policy**, paste the agent's **public key**, set its limits, and review the transaction in the wallet. The agent private key stays in its runtime.
5. Open **Code setup** and use **Copy setup** for your runtime. **Check connection** checks the available setup; it does not prove a facilitator will accept a future payment.
6. Make a compatible paid request with the SDK or MCP. Finalized payments appear in **Activity** when verified indexing and the explicit public feed are configured below.
7. Use **Freeze** or **Resume** for an agent and confirm in the owner wallet. Wait for the on-chain state before treating the action as complete.

Existing policy keys are visible, copyable, and immutable. Editing limits preserves consumed budget, freeze state, window timing, and unchanged payment spacing. The browser verifies that wallet-signed policy transactions match the reviewed intent before submitting them. The app never receives the owner's private key.

A freeze takes effect in chain order. It cannot reverse a payment that executed first, and cancellation cannot undo a transaction already submitted. Reconcile an uncertain transaction before submitting another.

## Enable verified public Activity

Server-side indexing uses authenticated webhook intake, independent finalized RPC verification, and Postgres. Follow the repository indexer setup to apply migrations, configure its deployed program/RPC/database, and track the intended vaults.

The dashboard's public read endpoint is **opt-in**:

```dotenv
BRIM_PUBLIC_ACTIVITY_ENABLED=true
BRIM_TRACKED_VAULTS=YOUR_EXPLICITLY_TRACKED_VAULT_ADDRESS
DATABASE_URL=YOUR_SERVER_ONLY_DATABASE_CONNECTION
```

`GET /api/activity?vault=<publicKey>` serves up to 50 settled records only for an explicitly tracked vault. It exposes chain fields such as signature, recipient, agent key, amount, and timestamp. It does not publish private merchant enrichment, agent names, or failed-attempt telemetry. Disabled and untracked feeds return `404`; invalid queries return `400`, and database failures return `503`.

This is a public chain-activity feed, not tenant authentication or a private corporate statement. Keep database and webhook credentials server-side. Settlement and indexing have separate timing: a successful resource response may arrive before the independently finalized Activity row.

## Local and Demo boundaries

`npm run dev` starts an offline Surfpool chain, Postgres, the dashboard, and the paid API. Local policy writes use the generated **test owner**, and **Make test payment** uses the starter agent. Successful local SDK/MCP `/report` settlements are queued automatically for finalized verification and indexing; the feed may update after the HTTP response. Pending work retries in the background and survives process restarts. If durable capture fails after settlement, the local API preserves the receipt and returns `503` with `SETTLED_INDEXING_UNAVAILABLE`; check that payment before requesting another.

Local funding, withdrawals, and freeze controls remain read-only. Demo workspace simulates controls in browser state. Neither path authorizes a production wallet or moves real funds. Local success and a mock Wallet Standard integration test do not establish public-network readiness.

## What remains before release

Deploy and verify the actual program and its upgrade authority, complete public devnet payments with the intended facilitator and real owner-wallet flows, test adversarial concurrency/replay, fuzz the contract, and obtain independent security review. Publish whether program upgrades are immutable or protected by documented multisig/timelock controls.

Production operations still need managed secrets, migrations/backups, pending-event reconciliation, monitoring, and any tenant authentication or private APIs the service promises. The GCP test deployment has keyless CI/CD and hosts the public site and demo dashboard; it does not provision live payment infrastructure. Squads CPI, Auto / Ask / Block approvals, passkeys, and a threat-driven freeze service remain separate follow-up work.
