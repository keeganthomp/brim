---
title: Vaults and spending policies
description: Give an existing agent a budget while keeping treasury control with its owner.
---

A vault holds USDC. Each agent uses its own signing key and an on-chain policy to spend from that vault. The treasury owner controls funding, policies, freezes, and withdrawals.

## Create a vault, then authorize an agent

The owner signs `init_vault` against a shared Brim program. It creates a program-derived vault account and an associated USDC token account controlled by that vault. Fund the token account; the vault account itself stores configuration.

Register an existing bot's public key with an owner-signed `upsert_agent_policy` instruction. The bot keeps its private key. It receives permission to make payments within that policy, without receiving the treasury key or a separate deployment of the program.

Agents share the vault balance. A $50 policy limits one agent's spending; it does not reserve $50 for that agent. Payments also require enough USDC in the vault.

## Register an existing agent locally

Keep `npm run dev` running and open **Local workspace** in the dashboard.

1. Choose **Add policy**.
2. Paste the existing agent's Ed25519 **public key**.
3. Set its **per-payment cap** and **24-hour budget**. Advanced controls hold payment spacing and approved recipients.
4. Choose **Add policy** and wait for confirmation. The server uses the generated Surfpool test owner to register that key on-chain.

The agent then appears in the list. Open its details to inspect or copy the registered public key and adjust limits. The key identifies this policy; an edit does not replace it. Policy edits retain consumed budget, freeze state, window timing, and unchanged payment spacing. A daily budget is a fixed 24-hour window, not a midnight reset.

Copy the same **vault config** for every agent on this vault. Each agent keeps its own private key in its runtime. See the [SDK steps](/docs/sdk/#register-your-agent-locally) for key generation and a paid report, or [MCP](/docs/mcp/#connect-your-own-local-agent).

This is an offline test-owner signing path. Local funding and freeze controls remain read-only; the separately configured [Live workspace](/docs/production/#follow-the-owner-wallet-flow) uses the actual vault owner wallet instead.

## Register through the configured owner wallet

[Configure the Live workspace](/docs/production/#configure-a-deployed-program) for an existing deployed program. Connect an ordinary Wallet Standard owner wallet, **Create vault** if absent, **Deposit** USDC, then **Add policy** using the agent's public key. Confirm each transaction in the wallet.

The policy sheet exposes the immutable, copyable public key. **Code setup → Copy setup** supplies public connection settings; the private agent key stays in its runtime. **Check connection** provides setup feedback without guaranteeing facilitator acceptance. Live **Freeze/Resume** and **Withdraw** use separate owner-wallet transactions. Squads-owned vault execution is not integrated.

## Set enforceable limits

These are the current policy fields, expressed in USDC base units. One USDC is `1_000_000` units.

```ts
const limits = {
  max_per_tx: 1_000_000n, // $1 per payment
  window_limit: 50_000_000n, // $50 per spending window
  window_duration: 86_400n, // 24 hours
  min_tx_interval: 6n, // At least 6 seconds between payments
  allowlist_enabled: true,
  allowlist: [process.env.MERCHANT_WALLET_ADDRESS!],
};
```

This object describes policy data. An owner must sign the corresponding program instruction to apply it; creating a JavaScript object changes no on-chain state.

| Control             | What the program checks                                               |
| ------------------- | --------------------------------------------------------------------- |
| Per-payment cap     | The requested amount is no greater than `max_per_tx`.                 |
| Window budget       | This payment plus spending in the current window fits `window_limit`. |
| Minimum interval    | Enough chain time has elapsed since the last successful payment.      |
| Recipient allowlist | The recipient wallet is allowed and its USDC token account matches.   |
| Freeze or pause     | The agent is not frozen and its vault is not paused.                  |

Allowlist entries are wallet addresses. Merchant domains are off-chain labels that the operator must map to verified recipients. An enabled, empty allowlist blocks every recipient.

## Understand when limits reset

A window starts when the policy is created. After it expires, the next accepted payment starts a new window at that payment's chain timestamp. A 24-hour window does not reset at midnight and does not continuously total the preceding 24 hours.

Minimum spacing is also literal: six seconds means a six-second gap between successful payments. It does not allow a burst of ten requests followed by a quiet minute.

Policy updates retain consumed budget, the window start, and the last payment timestamp. The current program does not allow changing a policy's window duration after creation.

## Freeze an agent

A freeze takes effect when its transaction executes. A pending payment that executes first can still settle; payments executing after the freeze must fail. Settled transfers cannot be reversed by freezing the agent. No fixed confirmation time is guaranteed.

Use **Freeze** or **Resume** and confirm the transaction in the owner wallet, then wait for on-chain state. Local controls remain read-only; Demo simulates them. The program also supports owner-only vault pause; owner withdrawals remain available while paused.

## Hand over the connection values

The integrator generates a scoped keypair and gives the operator its public key. The operator registers that public key with a policy, then shares a public `BRIM_VAULT_CONFIG` string. The integrator keeps the matching private keypair in its agent runtime as `BRIM_AGENT_KEY`.

Several agents can share the same public vault config when they use the same vault, program, network, and trusted fee payers. Their distinct keys select their individual policies.

Follow the [SDK handoff guide](/docs/sdk/#who-hands-over-what) for exact value formats, the operator's `createBrimVaultConfig` step, and the current dashboard template behavior. The same values also connect through [MCP](/docs/mcp/).

The local workspace reads real Surfpool balances and verified payment rows and can submit test-owner policy registration and updates. Funding and freezes remain read-only. The separate demo simulates policy, funding, and freeze controls; a public key is optional in a demo policy. See [production readiness](/docs/production/) before connecting real funds.
